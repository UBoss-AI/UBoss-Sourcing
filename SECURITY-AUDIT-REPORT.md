# UBOSS Security Audit Report

Audit date: 19 September 2026

Result: **Do not release this working copy to production yet.** The project has many good security controls, but the red and yellow items below must be handled. No source-code audit can guarantee that nobody will ever hack a system.

Scope reviewed: backend, all three web applications, scripts, dependencies and lockfiles, authentication, permissions, tenant isolation, payments, webhooks, uploads, database access, CI, nginx, systemd, deployment configuration, and the local development configuration. Secret values were not printed or copied into this report.

Status meaning: **Yes** = following; **Partly** = control exists but is incomplete; **No** = not following; **Not verified** = the repository cannot prove the live setting.

| Passwords use a modern password hash | **Yes** — Argon2id is used; unknown-user login also performs a dummy hash to reduce account discovery. | Keep Argon2 parameters reviewed as hardware changes. |
| Login brute-force and account lockout are controlled | **Yes** — attempts and lockout are stored in MariaDB and therefore work across API instances. | Monitor lockout abuse and alert on unusual failure spikes. |
| Sessions and refresh tokens are protected | **Yes** — separate audiences/cookies, signed `httpOnly` cookies, production `Secure`, token rotation, reuse detection, and server-side revocation exist. | Keep session-reuse alerts and test logout/password-change revocation in every release. |
| Cookie-authenticated changes have CSRF protection | **Yes** — double-submit CSRF protection is applied to unsafe requests. | Keep CSRF regression tests and never exempt new mutation routes without a documented reason. |
| CORS allows only trusted sites | **Yes** — exact configured origins are used; there is no wildcard with credentials. | Review the origin list whenever a new frontend/domain is added. |
| Authorization and tenant isolation are server-side | **Yes** — admin permissions, customer ownership, seller scope, logistics assignments, and separate token audiences are enforced on the server. Focused tenant tests passed. | Continue adding “tenant A cannot read tenant B” tests for every new object and route. |
| SQL injection is prevented | **Yes** — production queries use Prisma parameterized/tagged queries; the only unsafe raw query found is test-only. | Keep unsafe raw SQL out of production code and review every new raw query. |
| Stored/reflected XSS is controlled | **Yes, with CSP action above** — React escaping is used, rich HTML is sanitized on write and again before rendering; all 11 focused sanitizer tests passed. | Keep the sanitizer allowlist small and enable enforcing CSP for defense in depth. |
| Server-side request forgery is controlled | **Yes** — outbound ERP requests block private, loopback, link-local, and metadata addresses; DNS is resolved and pinned, and redirects are revalidated. | Keep private-target mode forbidden in production and retain SSRF regression tests. |
| Payment and ERP/carrier webhooks are authenticated | **Yes** — signatures use the raw body, constant-time comparison, freshness/replay checks, and idempotent event records. | Rotate webhook secrets periodically and alert on repeated signature failures. |
| Raw card data is kept out of the application | **Yes** — hosted payment components/tokens are used; the application stores provider references rather than card number/CVV. | Confirm the same behavior with a production-like payment test and review logs after it. |
| Sensitive stored integration credentials are encrypted | **Yes** — AES-256-GCM is used and the configuration requires a 32-byte key. | Protect and back up the encryption key separately; create a tested re-encryption/key-rotation procedure. |
| Secrets are not committed as real `.env` files | **Yes, with a development warning** — backend and compatibility `.env` files are ignored; tracked frontend `.env` files contain public Vite configuration. Keep development credentials limited to local-only data and remove hardcoded passwords from browser-automation scripts where practical. |
| Secret scanning covers repository history | **Partly / Not verified** — full-history gitleaks is configured in CI, but its latest successful run and GitHub push protection were not visible locally. | Confirm the job is green and required. Enable GitHub push protection and rotate any finding; deleting a secret from Git is not sufficient. |
| Logs and errors avoid sensitive data exposure | **Yes in code** — structured logging redacts authorization, cookies, payment signatures, passwords, tokens, MFA secrets, coordinates, and stored credentials; 500 responses hide internals. | Verify production log samples and access controls; add new secret field names to redaction immediately. |
| Uploads use type, size, name, and serving controls | **Partly** — magic bytes, allowlists, generated storage keys, size limits, signed links, attachment serving, `nosniff`, and strict media CSP exist; malware scanning is missing. | Preserve the existing controls and complete quarantine/scanning before users or staff can download documents. |
| Production configuration fails closed | **Yes in code** — production rejects insecure cookies, local storage, log-only email, placeholder secrets, private ERP targets, non-HTTPS sensitive redirects, and test payment keys. | Add a deployment check that starts the exact production environment and proves validation passes before traffic is switched. |
| Host processes run with least privilege | **Yes in configuration** — dedicated `uboss` user, `NoNewPrivileges`, strict filesystem protection, private devices/tmp, and narrow write paths are defined. | Verify the installed units match Git and review them with `systemd-analyze security`. |
| Database and services are not directly public | **Yes in configuration** — production/compat designs bind API/database services to loopback and nginx supplies the public edge. | Confirm on the live host with `ss` and an external port scan after every infrastructure change. |
| Database privileges protect schema and audit records | **Yes in deployment design / Not verified live** — separate runtime/migration grants and append-only audit protections are documented. | Inspect actual grants on production and prove the runtime user cannot run DDL or alter/delete protected audit rows. |
| Security headers are present | **Yes, except web CSP enforcement** — HSTS, frame denial, MIME sniffing protection, referrer policy, permissions policy, and strict API/media CSP are configured. | Enable the web CSP action above and verify headers on every response path, including errors and cached assets. |
| CI creates dependency evidence | **Partly** — npm audit and CycloneDX SBOMs exist for the four runtime apps, but not `scripts`. | Add `scripts`, retain SBOMs for each release, and define who responds when an advisory is published. |
| Frontend security-related checks are green | **Yes** — type-check, lint, and contrast checks passed; admin 40/40 tests, customer 736/736 tests, and logistics 71/71 tests passed outside the restricted test sandbox. | Clean up React `act(...)` test warnings and also run production builds in the release pipeline. |

## Test evidence

- Production dependency audits: **0 known vulnerabilities** in backend, admin web, customer web, logistics web, and scripts production dependencies.
- Full dependency audit: **1 high** development-tool vulnerability in `scripts`; all other audited packages were clear.
- Focused backend security tests: **171 passed** — authentication, token rotation/reuse, TOTP, SSRF, payment security, signed carrier webhooks, and logistics tenant isolation.
- Frontend tests: **847 passed** across the three web applications, including **11 XSS sanitizer tests**.
- Backend type-check and lint: passed.
- Full backend test command: **not green** in this working copy; broad failures occurred when suites ran together, while focused files passed independently.
- Local gitleaks, Semgrep, and Trivy executables were not installed. CI configuration was inspected, but its latest remote run was not available in this local audit.

## Standard used

The checklist is based mainly on the [OWASP Application Security Verification Standard 5.0.0](https://owasp.org/projects/asvs), the [OWASP File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html), and [NIST Secure Software Development Framework SP 800-218](https://csrc.nist.gov/pubs/sp/800/218/final).

## Final decision

The architecture has a good security foundation, but it is **not ready for a production security sign-off**. At minimum, fix the failed full test gate, vulnerable scripts dependency/CI omission, malware scanning, admin MFA, local network exposure of seeded accounts, and enforcing CSP; then validate the real production server and commission an independent penetration test.
